Chapter 1

Why Quantum Resistance Matters Now

The threat is no longer theoretical

The Quantum Threat to Ethereum

In March 2026, Google published a landmark paper demonstrating that breaking the secp256k1 elliptic curve — the curve that secures every Ethereum transaction — requires approximately 1,200 logical qubits (mapped to roughly 500,000 physical qubits). Their estimate: an attacker with that hardware could derive a private key from a public key in under 9 minutes.

To put this in perspective, Google's current Willow processor has 105 physical qubits. We need roughly a 5,000x increase in qubit count — a gap that, given the exponential pace of quantum hardware scaling, could close within a decade. The cryptographic community's consensus: the time to prepare is now, not when the hardware arrives.

Harvest Now, Decrypt Later
Adversaries are already recording encrypted blockchain data today, planning to decrypt it when quantum computers become available. Every ECDSA signature reveals the public key, creating a permanent record of vulnerability. Transactions signed today can be targeted tomorrow.

NIST Mandates and Timelines

The U.S. National Institute of Standards and Technology has drawn a line in the sand. Their mandate is straightforward:

  • By 2030: Deprecate all quantum-vulnerable algorithms (ECDSA, RSA, DSA) in federal systems
  • By 2035: Completely disallow these algorithms

NIST has finalized three post-quantum standards: FIPS 203 (ML-KEM, for key encapsulation), FIPS 204 (ML-DSA / Dilithium, for digital signatures), and FIPS 206 (SLH-DSA / Falcon, for digital signatures). These are not proposals — they are published standards that organizations are expected to adopt.

For Ethereum, this matters because institutional adoption depends on compliance with these standards. Exchanges, custodians, and financial institutions that touch regulated markets must follow NIST guidance. A quantum-vulnerable Ethereum becomes a compliance risk.

Ethereum's Strawmap

The Ethereum Foundation has published a "Strawmap" — a phased roadmap for achieving full post-quantum resistance. The plan spans 7 hard forks over 4 years, targeting complete PQ resistance by 2030:

  1. Phase 1 (2026): PQC precompiles for signature verification (EIP-8051 for Dilithium, EIP-8052 for Falcon)
  2. Phase 2 (2027): Replace BLS signatures in the beacon chain consensus
  3. Phase 3 (2028): Migrate KZG commitments to PQ-safe alternatives for data availability
  4. Phase 4 (2029-2030): Replace Groth16 ZK proofs with PQ-safe proving systems

The precompile EIPs (8051 and 8052) are particularly relevant to this tutorial. They propose native Dilithium and Falcon verification at approximately 3,000 gas — the same cost as ECDSA today. Until those ship, we build with pure-Solidity verifiers.

The Migration Path: Account Abstraction

The key insight that makes all of this possible today is account abstraction. Through ERC-4337 and the newer EIP-7702, Ethereum already supports smart contract accounts with custom signature verification logic.

Chapter 2

Lamport Signatures from Scratch

Quantum resistance using nothing but hash functions

How Lamport Signatures Work

Lamport signatures, invented by Leslie Lamport in 1979, are the simplest post-quantum signature scheme. Their security relies entirely on the preimage resistance of a hash function — if you can't reverse keccak256, you can't forge a signature. No lattices, no curves, no number theory. Just hashing.

Key Generation

Generate 256 pairs of random 32-byte values (512 values total). Hash each one. The 512 hashes are your public key. The 512 original values are your private key.

Private Key (keep secret)          Public Key (publish)
===========================        ===========================
Pair 0:  [left_0,  right_0]  -->  [H(left_0),  H(right_0)]
Pair 1:  [left_1,  right_1]  -->  [H(left_1),  H(right_1)]
  ...         ...                       ...
Pair 255:[left_255,right_255] -->  [H(left_255),H(right_255)]
256 pairs → 512 secret values → 512 public hashes

Signing

To sign a message, hash it to get a 256-bit digest. For each bit of the digest:

  • If bit i is 0: reveal left_i (the left preimage from pair i)
  • If bit i is 1: reveal right_i (the right preimage from pair i)

The signature is 256 revealed preimages (256 × 32 bytes = 8,192 bytes).

Verification

Hash each of the 256 revealed preimages and compare against the corresponding public key hash. If all 256 match, the signature is valid.

One-Time Use Only
Each Lamport key pair can only sign one message. Signing a second message reveals additional preimages, allowing an attacker to forge signatures. Our LamportAccount handles this by using a Merkle tree of many key pairs and tracking which ones have been used.

LamportVerifier.sol

The verifier implements the core algorithm: loop through 256 bits, hash each preimage, compare against the public key. It also includes a verifyWithRoot() variant that checks a Merkle root of the public key hashes, enabling compact on-chain storage.

src/lamport/LamportVerifier.sol 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.25;

/// @title LamportVerifier — Quantum-resistant signature verification using only keccak256
/// @notice Lamport one-time signatures: the simplest post-quantum scheme.
///         Security relies solely on hash preimage resistance — no lattices, no curves.
contract LamportVerifier {
    /// @notice Verify a Lamport signature against a public key
    function verify(
        bytes32 msgHash,
        bytes32[512] calldata pubKeyHashes,
        bytes32[256] calldata signature
    ) external pure returns (bool valid) {
        for (uint256 i = 0; i < 256; i++) {
            // Extract bit i from the message hash
            uint256 bit = (uint256(msgHash) >> (255 - i)) & 1;

            // Hash the revealed preimage
            bytes32 computed = keccak256(abi.encodePacked(signature[i]));

            // Compare against the correct public key hash
            bytes32 expected = pubKeyHashes[2 * i + bit];

            if (computed != expected) {
                return false;
            }
        }
        return true;
    }

    /// @notice Verify using a compact Merkle root instead of the full 512-hash public key
    function verifyWithRoot(
        bytes32 msgHash,
        bytes32 pubKeyRoot,
        bytes32[512] calldata pubKeyHashes,
        bytes32[256] calldata signature
    ) external pure returns (bool valid) {
        // Verify the public key hashes match the stored root
        bytes32 computedRoot = _computeMerkleRoot(pubKeyHashes);
        if (computedRoot != pubKeyRoot) {
            return false;
        }

        // Then verify the signature against those hashes
        for (uint256 i = 0; i < 256; i++) {
            uint256 bit = (uint256(msgHash) >> (255 - i)) & 1;
            bytes32 computed = keccak256(abi.encodePacked(signature[i]));
            bytes32 expected = pubKeyHashes[2 * i + bit];
            if (computed != expected) {
                return false;
            }
        }
        return true;
    }

    /// @notice Compute the Merkle root of 512 leaf hashes
    function _computeMerkleRoot(bytes32[512] calldata leaves) internal pure returns (bytes32) {
        bytes32[512] memory layer;
        for (uint256 i = 0; i < 512; i++) {
            layer[i] = leaves[i];
        }

        uint256 n = 512;
        while (n > 1) {
            for (uint256 i = 0; i < n / 2; i++) {
                layer[i] = keccak256(abi.encodePacked(layer[2 * i], layer[2 * i + 1]));
            }
            n /= 2;
        }
        return layer[0];
    }
}

LamportAccount.sol

The account contract wraps the verifier into an ERC-4337 compatible smart account. It stores a Merkle root of Lamport public keys and tracks which key index to use next. Each validateUserOp call verifies one Lamport signature and advances the key index.

src/lamport/LamportAccount.sol 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.25;

import {IAccount, UserOperation} from "../interfaces/IAccount.sol";
import {LamportVerifier} from "./LamportVerifier.sol";

/// @title LamportAccount — Quantum-resistant smart account using Lamport signatures
/// @notice ERC-4337 compatible account that verifies Lamport one-time signatures.
///         Uses a Merkle tree of Lamport public keys to support multiple transactions.
contract LamportAccount is IAccount {
    LamportVerifier public immutable verifier;
    bytes32 public publicKeyRoot;
    uint256 public nextKeyIndex;
    address public owner;
    uint256 public nonce;

    uint256 internal constant SIG_VALIDATION_FAILED = 1;

    event KeyRootUpdated(bytes32 indexed newRoot);
    event Executed(address indexed target, uint256 value, bytes data);

    error OnlyOwner();
    error OnlyEntryPointOrOwner();
    error InvalidSignature();
    error ExecutionFailed();

    modifier onlyOwner() {
        if (msg.sender != owner) revert OnlyOwner();
        _;
    }

    constructor(address _verifier, bytes32 _publicKeyRoot, address _owner) {
        verifier = LamportVerifier(_verifier);
        publicKeyRoot = _publicKeyRoot;
        owner = _owner;
    }

    /// @notice ERC-4337 signature validation
    /// @dev Signature format: abi.encode(bytes32[512] pubKeyHashes, bytes32[256] lamportSig)
    function validateUserOp(
        UserOperation calldata userOp,
        bytes32 userOpHash,
        uint256 missingAccountFunds
    ) external override returns (uint256 validationData) {
        // Decode the Lamport signature from userOp.signature
        (bytes32[512] memory pubKeyHashes, bytes32[256] memory lamportSig) =
            abi.decode(userOp.signature, (bytes32[512], bytes32[256]));

        // Verify the Lamport signature against the userOp hash
        bool valid = verifier.verifyWithRoot(userOpHash, publicKeyRoot, pubKeyHashes, lamportSig);

        if (!valid) {
            return SIG_VALIDATION_FAILED;
        }

        // Increment key index (each Lamport key is one-time use)
        nextKeyIndex++;
        nonce++;

        // Pay the EntryPoint if needed
        if (missingAccountFunds > 0) {
            (bool success,) = payable(msg.sender).call{value: missingAccountFunds}("");
            (success); // ignore failure (EntryPoint will handle it)
        }

        return 0; // success
    }

    /// @notice Execute a call from this account
    function execute(address target, uint256 value, bytes calldata data) external {
        (bool success,) = target.call{value: value}(data);
        if (!success) revert ExecutionFailed();
        emit Executed(target, value, data);
    }

    /// @notice Update the Lamport key tree root (for key rotation)
    function updateKeyRoot(bytes32 newRoot) external onlyOwner {
        publicKeyRoot = newRoot;
        nextKeyIndex = 0;
        emit KeyRootUpdated(newRoot);
    }

    receive() external payable {}
}

Tests

The test file demonstrates key generation, signing, and verification entirely on-chain. It uses deterministic seeds for reproducibility and includes gas measurement.

test/lamport/LamportVerifier.t.sol 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.25;

import "forge-std/Test.sol";
import "../../src/lamport/LamportVerifier.sol";

contract LamportVerifierTest is Test {
    LamportVerifier public verifier;

    function setUp() public {
        verifier = new LamportVerifier();
    }

    /// @notice Generate a deterministic Lamport keypair from a seed
    function _generateKeypair(bytes32 seed)
        internal pure
        returns (bytes32[512] memory pubKeyHashes, bytes32[512] memory privateKeys)
    {
        for (uint256 i = 0; i < 512; i++) {
            privateKeys[i] = keccak256(abi.encodePacked(seed, i));
            pubKeyHashes[i] = keccak256(abi.encodePacked(privateKeys[i]));
        }
    }

    /// @notice Sign a message hash using a Lamport private key
    function _sign(bytes32 msgHash, bytes32[512] memory privateKeys)
        internal pure
        returns (bytes32[256] memory signature)
    {
        for (uint256 i = 0; i < 256; i++) {
            uint256 bit = (uint256(msgHash) >> (255 - i)) & 1;
            signature[i] = privateKeys[2 * i + bit];
        }
    }

    function test_VerifyValidSignature() public view {
        bytes32 seed = keccak256("test-seed-1");
        (bytes32[512] memory pubKeyHashes, bytes32[512] memory privateKeys) = _generateKeypair(seed);

        bytes32 msgHash = keccak256("hello quantum world");
        bytes32[256] memory signature = _sign(msgHash, privateKeys);

        bool valid = verifier.verify(msgHash, pubKeyHashes, signature);
        assertTrue(valid, "Valid Lamport signature should verify");
    }

    function test_RejectInvalidSignature() public view {
        bytes32 seed = keccak256("test-seed-2");
        (bytes32[512] memory pubKeyHashes, bytes32[512] memory privateKeys) = _generateKeypair(seed);

        bytes32 msgHash = keccak256("hello quantum world");
        bytes32[256] memory signature = _sign(msgHash, privateKeys);

        // Corrupt one preimage
        signature[0] = bytes32(uint256(signature[0]) ^ 1);

        bool valid = verifier.verify(msgHash, pubKeyHashes, signature);
        assertFalse(valid, "Corrupted signature should fail verification");
    }

    function test_RejectWrongMessage() public view {
        bytes32 seed = keccak256("test-seed-3");
        (bytes32[512] memory pubKeyHashes, bytes32[512] memory privateKeys) = _generateKeypair(seed);

        bytes32 msgHash = keccak256("original message");
        bytes32[256] memory signature = _sign(msgHash, privateKeys);

        bytes32 wrongHash = keccak256("different message");
        bool valid = verifier.verify(wrongHash, pubKeyHashes, signature);
        assertFalse(valid, "Signature for wrong message should fail");
    }

    function test_VerifyWithMerkleRoot() public view {
        bytes32 seed = keccak256("test-seed-4");
        (bytes32[512] memory pubKeyHashes, bytes32[512] memory privateKeys) = _generateKeypair(seed);

        bytes32 msgHash = keccak256("merkle root test");
        bytes32[256] memory signature = _sign(msgHash, privateKeys);

        bytes32 root = _computeRoot(pubKeyHashes);

        bool valid = verifier.verifyWithRoot(msgHash, root, pubKeyHashes, signature);
        assertTrue(valid, "Valid signature with correct Merkle root should verify");
    }

    function test_RejectWrongMerkleRoot() public view {
        bytes32 seed = keccak256("test-seed-5");
        (bytes32[512] memory pubKeyHashes, bytes32[512] memory privateKeys) = _generateKeypair(seed);

        bytes32 msgHash = keccak256("merkle root test");
        bytes32[256] memory signature = _sign(msgHash, privateKeys);

        bytes32 wrongRoot = keccak256("wrong root");

        bool valid = verifier.verifyWithRoot(msgHash, wrongRoot, pubKeyHashes, signature);
        assertFalse(valid, "Wrong Merkle root should fail");
    }

    function test_GasCost() public {
        bytes32 seed = keccak256("gas-test");
        (bytes32[512] memory pubKeyHashes, bytes32[512] memory privateKeys) = _generateKeypair(seed);

        bytes32 msgHash = keccak256("measure gas");
        bytes32[256] memory signature = _sign(msgHash, privateKeys);

        uint256 gasBefore = gasleft();
        verifier.verify(msgHash, pubKeyHashes, signature);
        uint256 gasUsed = gasBefore - gasleft();

        emit log_named_uint("Lamport verify gas", gasUsed);
        assertLt(gasUsed, 500_000, "Lamport verification should cost less than 500K gas");
    }

    /// @dev Mirror the contract's Merkle root computation for test assertions
    function _computeRoot(bytes32[512] memory leaves) internal pure returns (bytes32) {
        bytes32[512] memory layer;
        for (uint256 i = 0; i < 512; i++) {
            layer[i] = leaves[i];
        }
        uint256 n = 512;
        while (n > 1) {
            for (uint256 i = 0; i < n / 2; i++) {
                layer[i] = keccak256(abi.encodePacked(layer[2 * i], layer[2 * i + 1]));
            }
            n /= 2;
        }
        return layer[0];
    }
}

Chapter 3

Production PQC — Falcon-512 with ETHFALCON

Lattice-based signatures, NIST standardized, EVM-verified

What is Falcon-512?

Falcon (Fast-Fourier Lattice-based Compact Signatures over NTRU) is one of three digital signature schemes standardized by NIST as FIPS 206. It is based on the hardness of the NTRU lattice problem and the Short Integer Solution (SIS) problem — problems that remain hard even for quantum computers.

Key properties of Falcon-512:

  • Signature size: ~666 bytes (the most compact of the NIST PQC signatures)
  • Public key size: ~897 bytes (stored in NTT domain for efficient verification)
  • Security level: NIST Level 1 (equivalent to AES-128)
  • Signing: Uses discrete Gaussian sampling over NTRU lattices
  • Verification: NTT-based polynomial arithmetic + hash checks

ZKNox's ETHFALCON Optimization

ETHFALCON by ZKNox is the first production EVM implementation of Falcon-512 verification. Their key optimization: replacing SHAKE-256 (the hash function in standard Falcon) with Keccak-256, which is a native EVM opcode. This single change eliminates the enormous gas overhead of simulating SHAKE in Solidity.

The result: Falcon signature verification in approximately 1.5 million gas. Expensive compared to ECDSA's 3,000 gas, but functional on any EVM chain today. The public key is stored using SSTORE2 (storing data as contract bytecode) to reduce storage costs.

Interface: ISigVerifier
ETHFALCON exposes a simple interface: setKey(bytes) stores a public key and returns an SSTORE2 pointer. verify(bytes, bytes32, bytes) checks a signature against a stored key and returns a success selector. Our FalconAccount wraps this interface into the ERC-4337 flow.

FalconAccount.sol

src/falcon/FalconAccount.sol 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.25;

import {IAccount, UserOperation} from "../interfaces/IAccount.sol";
import {ISigVerifier} from "InterfaceVerifier/IVerifier.sol";

/// @title FalconAccount — Quantum-resistant smart account using Falcon-512 (ETHFALCON)
/// @notice ERC-4337 compatible account that verifies Falcon-512 lattice-based signatures.
///         Uses ZKNox's ETHFALCON variant (Keccak instead of SHAKE) for ~1.5M gas verification.
contract FalconAccount is IAccount {
    ISigVerifier public immutable falconVerifier;
    address public owner;
    uint256 public nonce;

    // Falcon public key stored as SSTORE2 pointer
    bytes public storedPubKeyPointer;

    // The raw public key data for reference
    bytes public rawPublicKey;

    uint256 internal constant SIG_VALIDATION_FAILED = 1;

    event Executed(address indexed target, uint256 value, bytes data);
    event PublicKeyUpdated();

    error OnlyOwner();
    error ExecutionFailed();
    error PublicKeyNotSet();

    modifier onlyOwner() {
        if (msg.sender != owner) revert OnlyOwner();
        _;
    }

    // ISigVerifier.verify.selector = bytes4(keccak256("verify(bytes,bytes32,bytes)"))
    bytes4 internal constant VERIFY_SUCCESS = 0x024ad318;

    constructor(address _falconVerifier, bytes memory _publicKey, address _owner) {
        falconVerifier = ISigVerifier(_falconVerifier);
        owner = _owner;

        // Store the public key via ETHFALCON's setKey (uses SSTORE2)
        if (_publicKey.length > 0) {
            storedPubKeyPointer = falconVerifier.setKey(_publicKey);
            rawPublicKey = _publicKey;
        }
    }

    /// @notice ERC-4337 signature validation using Falcon-512
    /// @dev Signature format: raw Falcon signature bytes (salt + s2 encoded)
    function validateUserOp(
        UserOperation calldata userOp,
        bytes32 userOpHash,
        uint256 missingAccountFunds
    ) external override returns (uint256 validationData) {
        if (storedPubKeyPointer.length == 0) revert PublicKeyNotSet();

        // Call ETHFALCON's ISigVerifier.verify(pubkey, hash, signature)
        bytes4 result = falconVerifier.verify(
            storedPubKeyPointer,
            userOpHash,
            userOp.signature
        );

        if (result != VERIFY_SUCCESS) {
            return SIG_VALIDATION_FAILED;
        }

        nonce++;

        // Pay the EntryPoint if needed
        if (missingAccountFunds > 0) {
            (bool success,) = payable(msg.sender).call{value: missingAccountFunds}("");
            (success);
        }

        return 0;
    }

    /// @notice Execute a call from this account
    function execute(address target, uint256 value, bytes calldata data) external {
        (bool success,) = target.call{value: value}(data);
        if (!success) revert ExecutionFailed();
        emit Executed(target, value, data);
    }

    /// @notice Update the Falcon public key
    function updatePublicKey(bytes memory newKey) external onlyOwner {
        storedPubKeyPointer = falconVerifier.setKey(newKey);
        rawPublicKey = newKey;
        emit PublicKeyUpdated();
    }

    receive() external payable {}
}

        bytes32 userOpHash = keccak256("test-falcon-op");

        mockVerifier.setShouldPass(true);

        uint256 result = account.validateUserOp(userOp, userOpHash, 0);
        assertEq(result, 0, "Valid signature should return 0");
        assertEq(account.nonce(), 1, "Nonce should increment");
    }

    function test_ValidateUserOp_InvalidSignature() public {
        UserOperation memory userOp = _buildUserOp(hex"CAFEBABE");
        bytes32 userOpHash = keccak256("test-falcon-op");

        mockVerifier.setShouldPass(false);

        uint256 result = account.validateUserOp(userOp, userOpHash, 0);
        assertEq(result, 1, "Invalid signature should return SIG_VALIDATION_FAILED");
        assertEq(account.nonce(), 0, "Nonce should NOT increment");
    }

    function test_Execute() public {
        address recipient = address(0xCAFE);
        account.execute(recipient, 1 ether, "");
        assertEq(recipient.balance, 1 ether);
    }

    function test_UpdatePublicKey_OnlyOwner() public {
        vm.prank(OWNER);
        account.updatePublicKey(hex"AABBCCDD");

        vm.prank(address(0xDEAD));
        vm.expectRevert(FalconAccount.OnlyOwner.selector);
        account.updatePublicKey(hex"EEEE");
    }

    function test_ValidatePaysFunds() public {
        UserOperation memory userOp = _buildUserOp(hex"CAFEBABE");
        bytes32 userOpHash = keccak256("pay-test");
        mockVerifier.setShouldPass(true);

        address entryPoint = address(this);
        uint256 balBefore = entryPoint.balance;

        account.validateUserOp(userOp, userOpHash, 0.1 ether);

        assertEq(entryPoint.balance - balBefore, 0.1 ether, "Should pay missingAccountFunds");
    }

    function _buildUserOp(bytes memory sig) internal view returns (UserOperation memory) {
        return UserOperation({
            sender: address(account),
            nonce: 0,
            callData: "",
            callGasLimit: 100000,
            verificationGasLimit: 5000000,
            preVerificationGas: 50000,
            maxFeePerGas: 1 gwei,
            maxPriorityFeePerGas: 1 gwei,
            signature: sig
        });
    }

    receive() external payable {}
}

Factory pattern, deterministic addresses, live deployment

PQCAccountFactory.sol

The factory uses CREATE2 for deterministic account addresses. Given the same salt and parameters, the account address is predictable before deployment — essential for counterfactual accounts in ERC-4337.

src/factory/PQCAccountFactory.sol 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.25;

import {LamportVerifier} from "../lamport/LamportVerifier.sol";
import {LamportAccount} from "../lamport/LamportAccount.sol";
import {FalconAccount} from "../falcon/FalconAccount.sol";

/// @title PQCAccountFactory — Deploys quantum-resistant smart accounts
/// @notice CREATE2 factory for deterministic account addresses.
///         Supports both Lamport (hash-based) and Falcon (lattice-based) accounts.
contract PQCAccountFactory {
    LamportVerifier public immutable lamportVerifier;
    address public immutable falconVerifierAddress;

    event LamportAccountCreated(address indexed account, address indexed owner);
    event FalconAccountCreated(address indexed account, address indexed owner);

    constructor(address _lamportVerifier, address _falconVerifier) {
        lamportVerifier = LamportVerifier(_lamportVerifier);
        falconVerifierAddress = _falconVerifier;
    }

    /// @notice Deploy a new Lamport smart account
    function createLamportAccount(
        bytes32 pubKeyRoot,
        address owner,
        uint256 salt
    ) external returns (LamportAccount account) {
        account = new LamportAccount{salt: bytes32(salt)}(
            address(lamportVerifier),
            pubKeyRoot,
            owner
        );
        emit LamportAccountCreated(address(account), owner);
    }

    /// @notice Deploy a new Falcon-512 smart account
    function createFalconAccount(
        bytes memory publicKey,
        address owner,
        uint256 salt
    ) external returns (FalconAccount account) {
        account = new FalconAccount{salt: bytes32(salt)}(
            falconVerifierAddress,
            publicKey,
            owner
        );
        emit FalconAccountCreated(address(account), owner);
    }

    /// @notice Compute the deterministic address of a Lamport account
    function getLamportAccountAddress(
        bytes32 pubKeyRoot,
        address owner,
        uint256 salt
    ) external view returns (address) {
        bytes32 hash = keccak256(
            abi.encodePacked(
                bytes1(0xff),
                address(this),
                bytes32(salt),
                keccak256(
                    abi.encodePacked(
                        type(LamportAccount).creationCode,
                        abi.encode(address(lamportVerifier), pubKeyRoot, owner)
                    )
                )
            )
        );
        return address(uint160(uint256(hash)));
    }
}

            address(lamportVerifier),
            falconVerifier
        );
        console.log("PQCAccountFactory:", address(factory));

        vm.stopBroadcast();
    }

What's Next

The road from 1.5M gas to 3,000 gas

Path to 3,000 Gas: The Falcon Precompile

Everything we built in this tutorial is a stopgap. The real game-changer is EIP-8052: a native Falcon-512 precompile at the protocol level. When this ships, verification drops from ~1.5M gas to approximately 3,000 gas — the same as ECDSA today.

Our FalconAccount contract is designed to be forwards-compatible. When EIP-8052 lands:

  1. Deploy a new ISigVerifier adapter that calls the precompile address
  2. Factory deploys new accounts pointing to the precompile adapter
  3. Existing accounts can upgrade their verifier (if implemented as upgradeable)

No changes to the account logic, the signature format, or the key material. The only difference is the verification cost collapses by 500x.

Hybrid ECDSA + Falcon During Transition

The migration to post-quantum won't happen overnight. During the transition period, a hybrid signature scheme offers the best of both worlds:

  • Require both an ECDSA signature and a Falcon signature in validateUserOp
  • If quantum computers never materialize at scale, you lose nothing — you still have ECDSA security
  • If they do, the Falcon signature protects you even if ECDSA is broken
  • Gas cost: ~1.5M + 3K = ~1.5M (the Falcon verification dominates)

This is the approach recommended by NIST for the transition period: don't replace, layer.

Naysayer Optimistic Verification

The most exciting optimization on the horizon is naysayer verification, developed by the Poqeth team. The core idea: instead of verifying the full signature on-chain, accept it optimistically and let anyone challenge a bad signature within a time window.

How it works:

  1. The signature is submitted with a bond
  2. Anyone can submit a fraud proof showing the signature is invalid
  3. If challenged successfully, the submitter's bond is slashed
  4. If the challenge window passes with no fraud proof, the signature is accepted

The on-chain cost drops to approximately 25,000 gas for any PQC scheme, regardless of the verification complexity. This works for Falcon, Dilithium, STARKs — anything.

EIP-7702 Delegation for Existing EOAs

What about the billions of dollars locked in existing Externally Owned Accounts? EIP-7702 (live on mainnet since the Pectra upgrade) allows an EOA to delegate its validation logic to a smart contract for a single transaction.

This means an existing EOA can:

  1. Point its validation to a PQC account contract
  2. Sign transactions with a Falcon or Lamport key
  3. Keep the same address and balance

No need to migrate funds. No new address. Just attach quantum-resistant signing to your existing account.
