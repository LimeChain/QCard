Chapter 2: Lamport Signatures from Scratch

Lamport signatures (1979) are the simplest post-quantum scheme. Security depends only on hash preimage resistance — if you can't reverse keccak256, you can't forge a signature. No lattices, no curves, no number theory.

How It Works

Key generation: Generate 256 pairs of random 32-byte values (512 total). Hash each one. The 512 hashes are your public key; the 512 originals are your private key.

Signing: Hash the message to get a 256-bit digest. For each bit i: if bit is 0, reveal the left preimage; if 1, reveal the right. The signature is 256 revealed preimages (8 KB).

Verification: Hash each revealed preimage and compare against the public key hash. 256 matches = valid.

Private Key (secret) Public Key (on-chain) ======================== ======================== Pair 0: [left_0, right_0] ---> [H(left_0), H(right_0)] Pair 1: [left_1, right_1] ---> [H(left_1), H(right_1)] ... ... Pair 255: [left_255, right_255] -> [H(left_255), H(right_255)] Signing message hash 1011...0: bit 0 = 1 --> reveal right_0 bit 1 = 0 --> reveal left_1 bit 2 = 1 --> reveal right_2 ...
One-Time Use Each key pair signs exactly one message. A second signature reveals more preimages, enabling forgery. Our account handles this with a Merkle tree of many key pairs, tracked by nextKeyIndex.

Why Lamport Is Special on EVM

The EVM has a native keccak256 opcode costing just 36 gas per hash. Other hash functions (SHA-256, SHAKE) must be emulated in Solidity at 10-100x the cost. Lamport uses nothing but keccak256, making it the cheapest PQC option on EVM:

  • 256 hashes × 36 gas = ~9,200 gas for the core verification loop
  • The rest is calldata (8 KB signature at 16 gas/byte = ~130K gas) and Merkle proof checking
  • Total: ~754K gas including Merkle root verification and state updates

The Core Verification Loop

This is the heart of the verifier — 10 lines that provide quantum resistance:

for (uint256 i = 0; i < 256; i++) {
    uint256 bit = (uint256(msgHash) >> (255 - i)) & 1;
    bytes32 computed = keccak256(abi.encodePacked(signature[i]));
    bytes32 expected = pubKeyHashes[2 * i + bit];
    if (computed != expected) return false;
}
return true;

The Smart Account

LamportAccount wraps the verifier into an ERC-4337 account. Key design decisions:

  • EntryPoint enforcement: Only the ERC-4337 EntryPoint can call validateUserOp
  • Nonce + leaf index tracking: Prevents replay attacks and ensures each Lamport key is used exactly once
  • Merkle proof per leaf: The signature includes a proof that this leaf belongs to the account's key tree
  • Owner-gated execute: Only the owner or EntryPoint can call execute()
function validateUserOp(UserOperation calldata userOp, bytes32 userOpHash, uint256 missingAccountFunds)
    external override returns (uint256)
{
    if (msg.sender != entryPoint) revert OnlyEntryPoint();
    if (userOp.nonce != nonce) return SIG_VALIDATION_FAILED;

    // Decode: 512 pub hashes + 256 preimages + leaf index + Merkle proof
    (bytes32[512] memory pubKeyHashes, bytes32[256] memory lamportSig,
     uint256 leafIndex, bytes32[] memory merkleProof)
        = abi.decode(userOp.signature, (bytes32[512], bytes32[256], uint256, bytes32[]));

    if (leafIndex != nextKeyIndex) return SIG_VALIDATION_FAILED;

    bool valid = verifier.verifyWithRoot(userOpHash, publicKeyRoot, pubKeyHashes, lamportSig, leafIndex, merkleProof);
    if (!valid) return SIG_VALIDATION_FAILED;

    nextKeyIndex++;
    nonce++;
    return 0;
}

What the tests prove

  • Corrupted preimage fails — flipping one bit causes rejection
  • Wrong message fails — signature for message A fails against message B
  • Replay rejected — same signature fails on second use (nonce advances)
  • Wrong leaf index fails — can't skip ahead or reuse a consumed leaf
  • Non-EntryPoint caller reverts — only the EntryPoint can trigger validation

Chapter 3: Falcon-512 with ETHFALCON

Lamport proves the concept; Falcon is production-grade. Falcon-512 (NIST FIPS 206) is a lattice-based signature scheme with the smallest signatures among NIST PQC standards — just 666 bytes vs 2,420 for Dilithium.

ZKNox's ETHFALCON Optimization

ETHFALCON by ZKNox (Ethereum Foundation-backed) is the key breakthrough. Standard Falcon uses SHAKE-256 for hashing, which costs ~1M gas to emulate on EVM. ETHFALCON replaces SHAKE with Keccak-256 (native opcode, 36 gas). Same security, 2.6x cheaper:

  • Naive Solidity Falcon: ~24M gas (impractical)
  • ZKNox ETHFALCON: ~1.5M gas (12x improvement via Yul NTT optimization + Keccak swap)
  • Future EIP-8052 precompile: ~3,000 gas (same as ECDSA)

The public key is stored via SSTORE2 (contract bytecode storage) to minimize gas. Verification calls ISigVerifier.verify(pubkeyPointer, hash, signature) and returns a magic selector on success.

FalconAccount

The account follows the same pattern as Lamport but calls the ETHFALCON verifier:

bytes4 result = falconVerifier.verify(storedPubKeyPointer, userOpHash, userOp.signature);
if (result != VERIFY_SUCCESS) return SIG_VALIDATION_FAILED;

Where VERIFY_SUCCESS = 0x024ad318 is the ISigVerifier.verify function selector, returned on success per the ZKNox convention.

src/falcon/FalconAccount.sol

Signing happens off-chain Falcon signing uses discrete Gaussian sampling with floating-point arithmetic — impossible on EVM. The ZKNox Python signer (sign_cli.py) handles key generation and signing. Only verification runs on-chain.

Test It

Chapter 4: End-to-End — From Key Generation to On-Chain PQC Transaction

This chapter walks through the complete flow: generate a quantum-resistant keypair, deploy the infrastructure, create your PQC account, sign a transaction with your Lamport key, submit it through a bundler, and verify it on-chain.

Two different keys are involved
  • ECDSA key (regular Ethereum private key) — used ONLY to deploy contracts and pay gas. This is your "infrastructure" key. It is NOT quantum-resistant.
  • Lamport seed (32-byte secret) — this IS your quantum-resistant key. It derives all Lamport keypairs. It never touches the blockchain directly — only the public key root (a hash) goes on-chain.
Think of it like building a vault: you use a regular key to install the lock (deploy), but the vault itself opens with a completely different mechanism (Lamport signatures).

Phase 1: Generate Your Quantum-Resistant Keypair

Before touching any blockchain, generate your Lamport key material:

Install the signer

python3 -m venv .venv
source .venv/bin/activate
pip install pycryptodome

Choose a seed and generate your keypair

The seed is your master secret. Everything derives from it. In production, use a CSPRNG. For this tutorial:

LAMPORT_SEED="my-quantum-resistant-secret-seed-$(date +%s)"
echo "YOUR SEED: $LAMPORT_SEED"

python3 signer/lamport_signer.py genkeys --seed "$LAMPORT_SEED" --leaf-count 16

Expected output:

Generated Lamport account from seed: my-quantum-resistant-secret-seed-...
  Leaf count:  16
  Per leaf:    512 private values / 512 public key hashes
  Signature:   256 revealed preimages (8192 bytes)
  Account root: 0xe88091cd...

16 leaves = 16 transactions before you need to rotate the key tree. For a PoC, this is plenty.

Get the public key root

This is the only thing that goes on-chain — a single 32-byte Merkle root representing your entire key tree:

PUB_ROOT=$(python3 signer/lamport_signer.py pubroot --seed "$LAMPORT_SEED" --leaf-count 16)
echo "Public key root: $PUB_ROOT"
Seed = private key. Lose it = lose everything. The seed is the ONLY secret. Store it securely (password manager, encrypted file, hardware backup). Anyone with the seed can sign transactions from your PQC account.

Phase 3: Create Your PQC Account

Now create the actual quantum-resistant smart account. The factory takes your Lamport public key root (from Phase 1) and deploys an account that only accepts Lamport signatures matching that root.

Create the Lamport account via factory

MY_ADDRESS=$(cast wallet address --private-key $PRIVATE_KEY)

cast send $FACTORY_ADDRESS \
  "createLamportAccount(bytes32,address,address,uint256)" \
  $PUB_ROOT $ENTRY_POINT_ADDRESS $MY_ADDRESS 0 \
  --rpc-url $BASE_SEPOLIA_RPC_URL --private-key $PRIVATE_KEY

The factory emits a LamportAccountCreated event with the account address. Find it:

# Get the predicted address
ACCOUNT_ADDRESS=$(cast call $FACTORY_ADDRESS \

  $PUB_ROOT $ENTRY_POINT_ADDRESS $MY_ADDRESS 0 \

Phase 4: Sign a Transaction with Your Lamport Key

This is the quantum-resistant part. You sign with the Lamport seed (not any ECDSA key). The signature contains 256 revealed hash preimages + a Merkle proof, totaling ~24 KB.

Construct and sign a UserOperation

For this PoC, we'll sign a simple ETH transfer. The userOpHash is what the EntryPoint computes from the UserOperation fields:

# Example: sign a test userOpHash (in production, compute this from the real UserOp)
USER_OP_HASH=0x$(python3 -c "import hashlib; print(hashlib.sha256(b'test-transfer').hexdigest())")

# Sign with Lamport leaf 0
python3 signer/lamport_signer.py sign \
  --seed "$LAMPORT_SEED" \
  --leaf-count 16 \
  --leaf-index 0 \
  --message "$USER_OP_HASH" > /tmp/lamport_sig.json

echo "Signature generated. Leaf 0 consumed."
echo "Merkle proof length: $(python3 -c "import json; d=json.load(open('/tmp/lamport_sig.json')); print(len(d['merkle_proof']))")"

Understand the signature format

The JSON output contains everything needed for userOp.signature:

{
  "public_key_hashes": [512 x bytes32],   // The Lamport public key for this leaf
  "signature": [256 x bytes32],           // The revealed preimages
  "leaf_index": 0,                        // Which leaf in the Merkle tree
  "merkle_proof": [N x bytes32]           // Proof that this leaf belongs to the account root
}

ABI-encoded as: (bytes32[512], bytes32[256], uint256, bytes32[])

Phase 5: Submit via Bundler

The signed UserOperation goes to an ERC-4337 bundler, which wraps it in a regular transaction and submits it to the EntryPoint contract.

Get a Pimlico API key

Sign up at dashboard.pimlico.io (free tier works for testnet). Get your API key and set it:

Submit the UserOperation

The bundler expects the full UserOperation as JSON-RPC. The signature field is the ABI-encoded Lamport signature from Phase 4:

# Check the bundler is alive and supports our EntryPoint
curl -s -X POST "$BUNDLER_URL" \
  -H "Content-Type: application/json" \

A full UserOp submission script would construct the calldata, estimate gas, ABI-encode the Lamport signature, and call eth_sendUserOperation. This is non-trivial — see permissionless.js for a TypeScript SDK that handles all of this, or adapt the custom account boilerplate with the Lamport signer.

Verify on BaseScan

After the bundler processes your UserOp, check sepolia.basescan.org. Search for your account address — you should see:

  • The ETH funding transaction
  • The UserOperation execution (once submitted via bundler)

Chapter 5: What's Next

Path to 3,000 Gas

EIP-8052 proposes a native Falcon precompile: 1,000 gas for hash-to-point + 2,000 gas for core verification = 3,000 gas total — the same as ECDSA's ecrecover today. When this ships, swap the verifier address in the factory and new accounts get 500x cheaper verification with zero changes to the signature format or key material.

EIP-7885 (NTT precompile) takes a different approach: accelerate the Number Theoretic Transform that all lattice-based schemes share. This benefits Falcon, Dilithium, and STARK verification simultaneously.

Neither is scheduled for a hard fork yet. The first All Core Devs PQ breakout call was February 4, 2026.

Naysayer Optimistic Verification: ~25K Gas

The Poqeth project (ACM ASIA CCS 2025) introduces a game-changer: optimistic verification. Instead of verifying every signature on-chain:

  1. Contract accepts the signature provisionally
  2. A challenge window opens (like optimistic rollups)
  3. Anyone can submit a compact "naysayer proof" pointing to the specific failing step
  4. Only the challenged step is re-executed on-chain

Result: ~25K gas for any PQC scheme in the happy path (no challenge). Trade-off: requires at least one honest watcher.

Hybrid ECDSA + Falcon

During transition, require both signatures in validateUserOp. If quantum never arrives, you lose nothing. If it does, Falcon protects you. Gas: ~1.5M (Falcon dominates). When precompiles ship, the overhead drops to ~6K total.

EIP-7702 for Existing EOAs

EIP-7702 (live since May 2025, Pectra fork) lets EOAs delegate to a PQC-verifying contract while keeping their address. But the ECDSA key remains active — a quantum attacker could re-delegate. EIP-7851 (draft) proposes ECDSA key deactivation to close this gap.
